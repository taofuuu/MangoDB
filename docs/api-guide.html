Start

How do I run the API?

Copy .env.example, fill three values, npm run dev.

cd apps/api
cp .env.example .env      # then set JWT_SECRET, DATABASE_URL, DIRECT_URL
npm run db:generate       # regenerate Prisma Client after any schema change
npm run dev               # http://localhost:4000
npm run typecheck         # must pass before you open a PR

Generate your own JWT_SECRET with the command inside .env.example. Never share one between people or environments.

How do I add an endpoint?

Schema in schemas/, handler in controllers/, path in routes/, mount once in routes/index.ts.

// schemas/company.schema.ts
export const updateSchema = z.object({
    company_name: z.string().min(1).max(255),
    email: z.email().max(100),
});

// controllers/company.controller.ts
export async function updateProfile(req: Request, res: Response) {
    const body = parseBody(updateSchema, req.body);   // typed, or throws

    const company = await prisma.company.findUnique({
        where: { company_id: Number(req.auth!.sub) },
    });
    if (!company) throw ApiError.notFound('Company not found');

    res.json(await prisma.company.update({
        where: { company_id: company.company_id }, data: body,
    }));
}

// routes/company.routes.ts
companyRoutes.patch('/me', requireAuth, updateProfile);

No try/catch and no async wrapper — Express 5 forwards a rejected promise to the error handler by itself. Keep the controller to handlers: a response shape or an error translation that a second endpoint would want belongs in lib/.

What happens to a request?

Two gates, then your handler. Every failure exits through one place.

Errors

How do I return an error?

Throw an ApiError. Never call res.status(4xx) yourself.

throw ApiError.conflict('Username already taken');
throw ApiError.notFound('Company not found');
throw ApiError.forbidden();

errorHandler is the only place in the API that sets a 4xx or 5xx status. That is what makes “did they use the right shape?” impossible to get wrong instead of a review question.

What does an error look like?

Always this, for every non-2xx response.

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Request body is invalid",
    "details": [ { "field": "email", "message": "Invalid email address" } ]
  }
}
  • code — for the program. The frontend switches on it.
  • message — for a human reading a log. Reword it freely.
  • details — only when individual fields failed, so a form can put each message beside its own input.

Success responses return the resource itself, unwrapped — res.json(company), never { data: company }. 204 with no body for a delete or a logout.

Which code do I use?

Seven, and they are the whole vocabulary.

CodeStatusUse for
BAD_REQUEST400Malformed, but not about one field
VALIDATION_FAILED400Field-level rejection — carries details
UNAUTHORIZED401No token, bad token, ended session
FORBIDDEN403Authenticated, but this role may not
NOT_FOUND404Unknown route, or a missing resource
CONFLICT409Existing data blocks the write — a taken username
INTERNAL500A bug. Never thrown by hand

Codes are a contract with the frontend, so they live in @mangodb/shared and both apps import them. Renaming one fails the build on both sides instead of reaching a user.

401 or 403?

401 = we do not know who you are. 403 = we know, and no.

A missing or broken token is never 403 — that would tell a user their login is broken when it is working perfectly. One case looks like 403 and is not: a correctly signed token carrying a role we never issue is 401, because verifyAccessToken rejects it before requireRole ever runs.

Input

How do I validate a request body?

Write a zod schema, call parseBody. Never hand-write if (!body.x).

// schemas/auth.schema.ts
export const registerSchema = z.object({
    username: z.string().min(3).max(50),
    email: z.email().max(100),
    password: z.string().min(8),
});

// the controller
const body = parseBody(registerSchema, req.body);   // typed, or throws

body.email is now a string to the compiler, and bad input never reaches the next line — parseBody throws VALIDATION_FAILED with one details entry per bad field, which is already the shape a form needs. For query strings use parseQuery, and for route params like req.params.portfolioId use parseParams — reach for z.coerce in both, since query and path values always arrive as strings.

Why isn't validation middleware?

Middleware would have to hand the parsed value back through req.body, which Express types as any.

The handler would then need a cast, and a cast is a promise the compiler cannot check. Calling the parser inside the handler keeps the schema's type all the way down. The cost is that the route file no longer shows the contract — a deliberate trade.

Auth

How do I protect a route?

requireAuth first, then requireRole. Order is not optional.

companyRoutes.get('/me', requireAuth, getMyProfile);

// admin routers guard once, so a new route cannot miss the check
adminRoutes.use(requireAuth, requireRole('admin'));

requireRole is a factory — it takes the roles and returns the middleware, so the parentheses are required. Dropping them hands Express the factory, which silently enforces nothing. It takes any number of roles: requireRole('provider', 'receiver').

How do I know who is calling?

req.auth, set by requireAuth: { sub, role, jti, exp }.

sub is the user id, role is one of provider | receiver | both | admin — see what a role grants. req.auth is not a real Express property — src/types/express.d.ts merges it into Express's own types so TypeScript accepts it.

How does the browser stay signed in?

An httpOnly cookie the API sets. The frontend never holds the token.

// src/lib/session.ts — every endpoint that issues a token goes through here
res.cookie('access_token', session.accessToken, {
    httpOnly: true,          // JS cannot read it, so a script cannot steal it
    sameSite: 'lax',         // not sent on a cross-site POST — this is what stops CSRF
    secure: NODE_ENV === 'production',
    maxAge: 60 * 60 * 1000,  // mirrors the 1 h token expiry
});

Three endpoints hand out a session — register, POST /auth/login, and a credential change — and all three go through sendSession. That is the whole point of it: when only login set the cookie, the other two quietly left the browser without one.

The frontend stores nothing. It used to keep the token in localStorage and attach it by hand — and the login page shipped without the line that stored it, so every page after login was signed out. A browser cannot forget to send a cookie, which is what makes that whole class of bug go away. apiFetch in apps/mangodb/lib/api.ts sets credentials: 'include' once, and no page thinks about auth again.

The web app calls the API at /api/…, not localhost:4000: next.config.ts proxies /api/* through, so the browser only ever talks to one origin. Same-origin means the cookie needs no CORS, and keeps working when the frontend and API deploy to different hosts — where a cross-site cookie would need SameSite=None and a CSRF token beside it.

The token is still in the response body too, for callers that are not a browser. Those send Authorization: Bearer <token> instead, and requireAuth accepts either — header first, cookie second.

Why is my token rejected?

Three gates, all answering 401. The message tells you which one.

MessageMeans
Missing or malformed Authorization headerNo Bearer <token> header and no access_token cookie — see how the browser stays signed in
Invalid or expired tokenBad signature, malformed, past exp, or a role we never issue
Session has endedSignature is fine — this token was logged out

Tokens minted before jti was added no longer verify at all. If you have a token saved from an old session, mint a new one.

What is in a token, and what protects it?

Public claims, protected by a signature — not by secrecy.

{ "sub": "u-1", "role": "provider", "iat": …, "exp": …, "jti": … }
  • The payload is not encrypted. Base64 is encoding. Anyone can paste a token into jwt.io and read it, so nothing secret goes in one.
  • The signature is what stops edits. HMAC-SHA256(header.payload, JWT_SECRET) is recomputed on every request; change one character and it stops matching.
  • The secret is the security of the whole system. Leak it and anyone can mint admin tokens. One per environment, in .env, gitignored.
  • They expire in 1h and there are no refresh tokens — the user logs in again.

How does an administrator log in?

POST /auth/admin/login — same body as the normal login, and it hands back the same { company, accessToken } pair and the same cookie.

curl -s -X POST localhost:4000/auth/admin/login \
  -H 'content-type: application/json' \
  -d '{"email":"admin@example.com","password":"..."}'

The two logins are mirrors. Each turns away exactly the accounts the other accepts, so a token from either one is never a surprise to the page that asked for it:

EndpointADMIN accountCompany account
POST /auth/login403 use the administrator login200
POST /auth/admin/login200403 not an administrator account

Why 403 and not 401 for the wrong kind of account: the password checked out, so we know who is calling — the answer is just no. A bad credential is still 401, with the same message and the same timing on both endpoints, because both call the same verifyCredentials. See 401 or 403.

It lives on /auth, not /admin, because everything under /admin is guarded by requireAuth — a login route there would need a token to get a token. Nothing else is special: the token carries role: "admin", and logout is the same endpoint for everyone.

There is still no way to create an administrator. No signup path can make one — registerSchema rejects ADMIN and the profile edit cannot change account_type — and the script that used to write the first one is not in the repo. Ask whoever set up your database.

How are passwords stored?

bcrypt hashes at cost 12. The plaintext is never stored and never recoverable.

$2b$12$XqR7fK2mN9pQ8rS4tU6vW.eY1zA3bC5dE7fG9hI0jK2lM4nO6pQ8
 ↑    ↑  ↑
 alg  cost salt + hash, packed together

bcrypt salts automatically, so two identical passwords produce different hashes and one cracked "password123" does not crack everyone. It is also deliberately slow — cost 12 means 212 iterations, ~250 ms per hash. The salt and cost live inside the output, so verifyPassword needs nothing but the stored hash. One asymmetry on empty input: verifyPassword returns false, but hashPassword throws — an empty password reaching the hasher is a bug, not a typo.

How does logout actually end a session?

POST /auth/logout puts the token's jti on a denylist, and clears the cookie. requireAuth then rejects it.

Dropping the cookie on its own revokes nothing — that token stays signed and unexpired, and anyone holding a copy keeps access for the rest of the hour. That is why logout is a request and not a client-side delete. The endpoint takes the jti off the verified token, not the body, so nobody can end someone else's session. It answers 204; a second call with the same token answers 401, because gate 3 stops it before the handler. Revocation is per token, so logging out on one device leaves your other sessions alone.

Where does the denylist live?

In Postgres — public.revoked_token, keyed by jti. It survives a restart and is shared between instances.

It was a Map in one process until US1-3, so a logged-out token worked again after any restart — and tsx watch restarts on every file save. Only the storage changed; nothing outside tokenDenylist.ts knows where entries live. The cost is that both functions are async, so requireAuth awaits one query per request. Pruning happens on logout, not on reads.

Accounts

How does a company register?

POST /auth/register, public, returns 201 with the company and a token.

curl -s -X POST localhost:4000/auth/register -H 'content-type: application/json' -d '{
  "company_name": "CodeCrafters", "username": "codecrafters",
  "email": "contact@codecrafters.com", "password": "correct horse battery",
  "phone": "021111111", "account_type": "PROVIDER",
  "company_type": ["SME", "Software House"]
}'

{"company":{"company_id":33,"company_name":"CodeCrafters","username":"codecrafters",
 "email":"contact@codecrafters.com","account_type":"PROVIDER",
 "company_type":["SME","Software House"], ...},
 "accessToken":"eyJhbGciOiJIUzI1NiIs..."}

This is the one response in the API that wraps its resource. Everything else returns the object itself; register returns two things, because it also logs you in — the token it returns is the same one /companies/me accepts, so the frontend does not have to call login straight after signup — and it sets the session cookie as well, so a browser is signed in the moment it registers. company_description, address, and website are the only optional fields. The password hash is never in the response: the handler names the columns it returns with an explicit select rather than deleting the field afterwards.

What is account_type, and how is it different from company_type?

account_type is one of PROVIDER, RECEIVER, BOTH. company_type is repeatable industry tags.

They read alike and are not alike. account_type is a single uppercase discriminator on company, and it decides which subtype row the company gets: PROVIDER gets a row in provider, RECEIVER one in receiver, and BOTH gets both. The seeded database follows that without exception — 9 providers, 9 receivers, 2 BOTH companies carrying both rows — and register keeps it, creating the company, its tags, and its subtype rows in one nested create, which is one transaction.

company_type lives in its own table, many rows per company: SME, Software House, FinTech, AI Lab, 16 distinct values in the seed data. Registration requires at least one. There is no ADMIN account type — the enum rejects it, so nobody can register themselves an admin.

How does a BOTH company pass a provider-only route?

requireRole compares what the role grants, not the role itself.

// src/auth/roles.ts
both: ['provider', 'receiver', 'both'],
admin: ['admin'],

The token role comes from account_type — BOTH becomes 'both' — and asking what a role may act as is a separate question from what it is. Without this a BOTH company would get 403 on both kinds of route, which is the opposite of what it signed up for. Note that admin grants only admin: it is not a superset, and a BOTH token still gets 403 from /admin/ping.

What happens when the username is already taken?

409 CONFLICT, with the offending field in details.

{"error":{"code":"CONFLICT","message":"Username or email already registered",
  "details":[{"field":"username","message":"This username is already registered"}]}}

Two things check, and both matter. assertCompanyIdentityAvailable in lib/companyIdentity.ts runs a case-insensitive lookup before the insert — that is the one that can report both username and email in details, since an index only fails on whichever column it reaches first.

The unique indexes are still the enforcement. Two registrations claiming one username can both clear the pre-check; the loser's insert is rejected, Prisma reports P2002, and the handler turns that into the same envelope. Reading the field out takes a little care: through the driver adapter the columns arrive as the index name (company_username_key) rather than in meta.target.

Register lowercases username and email before writing, because the Postgres unique index is case-sensitive — without that, CodeCrafters would register happily alongside codecrafters.

How does a company edit its profile?

PATCH /companies/me. Send only what changed; null clears a nullable column.

curl -s -X PATCH localhost:4000/companies/me -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{
  "company_name": "CodeCrafters Co., Ltd.",
  "address": null,
  "company_type": ["SME", "AI Lab"]
}'

Three states, not two. A field that is absent leaves its column alone — that is what makes this a PATCH, and it is why the edit form may send one input or all of them. A field carrying a value overwrites. A field set to null clears, and only the six nullable columns accept it — company_description, address, website, contact_email, service_term, and warranty_policy; null anywhere else is a 400. An empty body is a 400 too — it is a client bug, not a no-op worth a 200.

company_type is a set, not a list you append to: the request carries the whole set and the tags it replaces are deleted. It is a nested write, so the delete and the create are one transaction and the company is never briefly untagged. Note the schema's .min(1) — there is no way to spend an edit removing every tag.

username and email are not editable here any more. They are the two halves of a login, so changing either needs the current password, and leaving them on an endpoint that never asks for one would make that gate decorative — anyone holding a token could walk around it with a single request. They moved to PATCH /companies/me/credentials, and this schema strips them silently, so {"email": "…"} alone is a 400 with nothing left to update.

There are two emails, and they are not the same thing. email is what a company signs in with: it is unique, and it is what POST /auth/login looks a company up by, so changing it changes the credential. contact_email is the address the profile shows so other companies can get in touch — nullable, not unique, and empty until someone fills it in, because registration never asks for one. Two companies sharing a contact address is a 200, not a 409. This endpoint writes contact_email only, which is why it needs no password; the account settings page changes email through PATCH /companies/me/credentials.

service_term and warranty_policy are the odd pair: they are columns on provider, not on company, so they only exist for a company that offers work. The controller writes them through a nested provider: { update: … } in the same transaction as the rest, and a RECEIVER company that sends either one gets a 403 — its account type owns no provider row to write to. A BOTH company is a provider too, which is why the check asks roleGrants rather than comparing the role to 'provider'. Reading them is always safe: a receiver simply sees null for both.

Four fields are not editable here, and the schema strips all four silently rather than rejecting the request. username, email, and password need the current password, so they live on PATCH /companies/me/credentials. account_type decides which subtype rows a company owns and what its token's role claim says, so changing it means writing provider/receiver rows and issuing a new token — still an endpoint nobody has written.

The response is the whole CompanyProfile, the same body GET /companies/me returns, so the form can render the saved state without a second request. Read-only mode is the frontend's job: the API has no draft state, and a profile the user is only looking at is simply one nobody sent a PATCH for.

How does a company change its username, email, or password?

PATCH /companies/me/credentials, with current_password every time.

curl -s -X PATCH localhost:4000/companies/me/credentials -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{
  "current_password": "correct horse battery",
  "email": "billing@codecrafters.com"
}'
{"company":{"company_id":33, …,"email":"billing@codecrafters.com", …},
 "accessToken":"eyJhbGciOiJIUzI1NiIs…"}

Partial like the profile edit — send any of username, email, and new_password, and an absent one is left alone. There is no null here, because none of the three columns is nullable. current_password on its own is a 400: it changes nothing, which is a client bug rather than a no-op worth a 200.

The current password gates all three, not just the password. Each one is a way to take an account over — move the email and you own the login, change the password and the owner is locked out — and a token is a bearer credential that can be copied out of localStorage. Requiring the password means holding the token is not enough. That is also the reason username and email came off PATCH /companies/me: a gate with a second, ungated door beside it is not a gate.

current_password uses the login rule, not the register rule — a length cap and nothing else. A password that predates a policy still has to authenticate, and a credential question must be answered with a 401, never a 400 that hands out the policy. new_password uses the register rule, since that one is being set: min(8) and the 72-byte bcrypt cap. Both live in companyFields as passwordAttempt and password, so register, login, and this endpoint cannot drift.

A wrong current_password is 401 UNAUTHORIZED, checked before anything is written, and no dummyPasswordHash dance is needed — the caller is already authenticated, so there is no account to enumerate by timing it. A username or email another company holds is 409 CONFLICT with one details entry per rejected field, the same assertCompanyIdentityAvailable pre-check registration uses — see what happens when the username is already taken. It is passed excludeCompanyId, or re-submitting your own value would collide with itself.

A successful change revokes the token it was made with, and returns a new one. That is the second response in the API that wraps, for register's reason inverted: it re-logs you in, because it just ended the session you were using. Revocation happens after the write, never before, so a wrong password or a 409 does not cost the caller its session. It revokes one jti, not every session the company holds — there is no per-company token version — so a copy of this token dies and a second device stays signed in until its own expires. The replacement rides back on the same response as a fresh cookie, so a browser stays signed in with nothing to do. Skipping that is not a small bug: the token the caller is holding was just revoked, so a company changing its own email would be signed out on its next click.

How does an administrator list and inspect Company accounts?

GET /admin/companies?page=1&pageSize=12 returns one page; GET /admin/companies/:companyId returns the selected account's full profile.

curl -s -H "Authorization: Bearer $TOKEN" \
  "localhost:4000/admin/companies?page=1&pageSize=12"

curl -s -H "Authorization: Bearer $TOKEN" \
  localhost:4000/admin/companies/33

Both routes currently require a valid session so private contact data is never public. Once US6-1 supplies administrator sessions, the router will add requireRole('admin') to restrict them to administrators.

Pages are ordered by company_name and then company_id so records do not jump between requests. page defaults to 1, pageSize defaults to 12 and is capped at 50. The response contains items plus pagination metadata with the current page, page size, total items and total pages.

The list returns only card fields and rating totals. The detail endpoint additionally returns username, sign-in email, contact email, phone, address, website and provider terms. Neither endpoint selects or returns the password hash.

Portfolios

How do I read a company's work samples?

GET /portfolios?companyId=4 — public, no token.

curl -s 'localhost:4000/portfolios?companyId=4'      # one company's rows
curl -s 'localhost:4000/portfolios?listingId=12'    # one listing's rows
curl -s localhost:4000/portfolios/7                 # one row by id

Both GETs are public: a work sample exists to be seen, and neither returns anything the profile page doesn't already show. That's why the front end reads them with no token, and why they sit above the requireAuth routes in portfolio.routes.ts.

listingId and companyId are both optional and can be combined. companyId filters through service → listing, the same chain assertPortfolioOwned walks, because the row has no owner column of its own. Leave both off and you get every row in the table — fine now, worth paginating later. The body is a bare array, ordered by development_date newest first.

development_date comes back as YYYY-MM-DD, not a timestamp: toServicePortfolio in src/lib/portfolio.ts slices the ISO string, so every route that returns a portfolio row agrees on the shape. Hand raw Prisma output to res.json() and you'd leak a T00:00:00.000Z the client has to strip.

How does a company add a work sample?

POST /portfolios — requireRole('provider'), and multipart/form-data rather than JSON, because it carries the image.

curl -s -X POST localhost:4000/portfolios -H "Authorization: Bearer $TOKEN"   -F 'listing_id=12'   -F 'portfolio_name=Inventory dashboard'   -F 'portfolio_description=Stock tracking for a small warehouse'   -F 'development_date=2026-05-01'   -F 'portfolio_link=https://example.com/work/inventory'   -F 'portfolio_image=@./shot.png'                  # 201

Note the -F flags, not -d. The file part is portfolio_image — PNG, JPEG or WebP, 5MB ceiling, enforced by uploadImage in src/middleware/upload.ts. The allowlist is deliberate rather than image/*: image/svg+xml is a document the browser runs scripts from once the public URL is opened. Everything else in the body arrives as a text part, which is why the schema leans on z.coerce for listing_id — form fields are always strings.

Ownership is checked before the upload, not after. A listing_id that isn't yours is 403 and an unknown one is 404, and in both cases nothing was written to storage yet. If the database insert fails afterwards, removeFromStorage deletes the file that was just written — otherwise a rejected request would leave an orphan in the bucket that nothing points at and nothing cleans up.

A portfolio_link the listing already carries is 409, the same @@unique([listing_id, portfolio_link]) that PATCH hits. The response is the created row, in the same shape the GETs return.

How does a company edit or remove a work sample (portfolio)?

PATCH /portfolios/:portfolioId and DELETE /portfolios/:portfolioId, both requireRole('provider').

curl -s -X PATCH localhost:4000/portfolios/7 -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{
  "portfolio_name": "Inventory dashboard",
  "development_date": "2026-05-01"
}'

curl -s -X DELETE localhost:4000/portfolios/7 -H "Authorization: Bearer $TOKEN"   # 204

There is no owner column on service_portfolio — the company is three hops away, service_portfolio → service → listing → company_id, so assertPortfolioOwned checks it as a nested Prisma select rather than a separate lookup. An unknown id is 404; a company checking someone else's portfolio is 403. The write itself repeats the same company_id filter in its own where, so a listing that changes hands in the gap between the check and the write can't slip through — Prisma finds nothing to update and the same 404 handling covers it.

PATCH is a partial update like /companies/me — send only what changed. portfolio_description is the only nullable field; every other field is required whenever it's present at all, and none accepts null. development_date takes a bare YYYY-MM-DD string — a full ISO timestamp fails validation rather than silently shifting the stored day across a timezone. portfolio_link accepts only http/https URLs. portfolio_image is not editable here: replacing the picture means uploading another file, which is the multipart POST, not this route.

A duplicate portfolio_link on the same listing is 409 — @@unique([listing_id, portfolio_link]) enforces it, the same P2002 pattern as the username/email conflict. DELETE is a hard delete: nothing references a portfolio row, and a soft-deleted one would keep occupying its slot in the unique index.

Layout

Where does code go?

Routes hold paths, controllers hold work, and nothing else holds either.

packages/shared/index.ts   UserRole · AccountType · CompanyProfile · ApiErrorCode · ApiErrorResponse

apps/api/src/
├── index.ts               6 lines — listens, nothing else
├── app.ts                 builds the app; does not listen
├── env.ts                 loads .env — first import, always
├── routes/                paths + middleware, no logic
├── controllers/           handlers, and nothing but handlers
├── schemas/               zod request schemas, one file per area
├── middleware/            auth · errorHandler · validate
├── lib/                   ApiError · prisma · prismaErrors · companyProfile · companyIdentity
├── auth/                  password · jwt · roles · tokenDenylist — pure, no HTTP
└── types/express.d.ts     teaches TypeScript about req.auth

auth/ holds pure functions that know nothing about HTTP, so a test can call them with no server running. middleware/ is the HTTP adapter. A controller that grows past its handlers is a sign something belongs in lib/: the register handler's response shape lives in lib/companyProfile.ts and its error translation in lib/prismaErrors.ts, so US1-4 does not rewrite either. packages/shared exists so the two apps cannot disagree — backend 'admin' vs frontend 'administrator' is a bug no compiler catches unless the type is defined once and imported by both.

Why is app.ts separate from index.ts?

app.ts builds the app but never calls listen, so a test can drive it with no port.

index.ts is the only file that opens a socket. This is the shape supertest needs; it exists so a test runner can be added without touching a single route.

Gotchas

Env vars are undefined

JavaScript runs every import before any other line, so dotenv loads after the import chain.

Two fixes coexist. jwt.ts defers the read: getSecret() reads JWT_SECRET at first use and throws if it is missing — signing with undefined would accept everyone's forgeries. lib/prisma.ts cannot defer, because it opens the connection while being imported, so load order is the fix: import './env' must be the first line of any entry point.

next() inside a try swallows every later error

Express runs the rest of the chain synchronously inside next(), so your catch catches their bugs.

try {
    req.auth = verifyAccessToken(token);
    next();                  // ← every downstream crash lands in the catch below
} catch {
    // a valid login gets told its token is bad; the real error vanishes
}

Keep only the throwing call inside the try and call next() after it. Watch for this shape wherever middleware wraps anything in try/catch.

Cannot find module '../generated/prisma/client'

Prettier formatted the generated client, then lint-staged's stash cleanup deleted it on commit.

npm run db:generate --workspace apps/api

The root .prettierignore now excludes apps/api/src/generated, so it should not recur. The directory is gitignored, so CI regenerates it before typecheck.

Three rows are worth staring at. The provider's logout left the admin session untouched — that is per-token revocation working. A forged role: admin token signed with a guessed secret was rejected, not accepted as an admin. And the email that differed from an existing one only in capitalisation was refused, which the database alone would have allowed. A fourth is worth adding: the token that changed a credential was dead on the very next request, while the one returned beside the company worked — that is the rotation, and it is what stops a copied token outliving the password change made to revoke it. The registrations above were run against the shared Supabase database and deleted afterwards. Other people's test rows are still in there, so the table holds more than the seeded 20 — delete your own when you finish a run.

Try it yourself

Two unrelated failures, one shape, and no handler formatted either.

curl -s localhost:4000/nope
{"error":{"code":"NOT_FOUND","message":"Cannot GET /nope"}}

curl -s localhost:4000/companies/me
{"error":{"code":"UNAUTHORIZED","message":"Missing or malformed Authorization header"}}

The quickest real token is a registration or a login — accessToken comes back in the response either way:

TOKEN=$(curl -s -X POST localhost:4000/auth/login -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"…"}' | npx json accessToken)

curl -s -H "Authorization: Bearer $TOKEN" localhost:4000/companies/me   # 200
curl -s -H "Authorization: Bearer $TOKEN" localhost:4000/admin/ping  # 403

Or skip the token and let curl behave like a browser, with a cookie jar. This is the path the web app takes: 

curl -s -c jar -X POST localhost:4000/auth/login -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"…"}' > /dev/null

curl -s -b jar localhost:4000/companies/me   # 200, no Authorization header
curl -s -b jar -X POST localhost:4000/auth/logout # 204, and the jar's cookie is cleared

To mint one by hand without an account at all — useful for a role you cannot register as, like admin: 

cd apps/api
TOKEN=$(npx tsx -e "import './src/env';
  import {signAccessToken} from './src/auth/jwt';
  console.log(signAccessToken({sub:'1',role:'provider'}))")

Missing

What does not exist yet?

Read this before assuming something works.

  • No signup page. The login page landed with US1-2 and signs you in for real — see how the browser stays signed in — but POST /auth/register still has no form in front of it. /dev/session in the web app is the stand-in: register a throwaway company there, then use it anywhere. Delete that route, and its dev_* rows, when /signup ships.
  • The seeded companies cannot log in even once login lands. All 20 carry the literal string hash123 in password, not a bcrypt hash, so verifyPassword rejects every one of them. The seed has to be rewritten.
  • No test runner. npm test is an exit 1 stub in the root and in apps/api. The table above came from a shell script — evidence, not a regression suite.
  • Nothing creates an administrator. account_type now accepts ADMIN and POST /auth/admin/login authenticates one, but no signup path can make one and the script that wrote the first is not in the repo. If your database has no admin row, ask whoever set it up.
  • No “log out everywhere”, no refresh tokens, no rate limiting, no request logging. Changing a password revokes only the token the change was made with — see the credentials endpoint — because revoking every session a company holds needs a per-company token version, and there is no column for one.
  • No route guard, and only one logout button. There is no middleware.ts, so an unauthenticated visitor reaches any page and each one handles its own 401 — account-settings and profile/edit hand-roll the same block. Logout exists only on /dev/session.
  • /admin/ping is a demonstration route, alive only until real endpoints replace it. /me is gone — US1-4 replaced it with GET /companies/me, US1-5 added PATCH beside it, and PATCH /companies/me/credentials now sits under both.
  • No way to change an account_type. PATCH /companies/me edits the profile and PATCH /companies/me/credentials the login identity, but moving a company between PROVIDER, RECEIVER, and BOTH means adding or removing subtype rows and restamping the token's role — still an endpoint nobody has written.
  • Nothing verifies a new email address. The change takes effect immediately, so a typo locks a company out of its own login until an admin fixes the row — and there is no admin. A confirmation link is the missing half.
