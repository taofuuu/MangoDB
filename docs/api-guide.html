    Chapter 01

    The auth spine

    Three small files decide who gets into the API and what they may do once inside. Every protected endpoint sits behind them.

    US1-1 · US1-2 · US6-1 9155d97 · 3af0532 bcryptjs · jsonwebtoken 12/12 cases verified

    Every protected request answers two questions

    They are different questions, and mixing them up is the most common beginner mistake. A valid admin and a valid provider are equally authenticated — they differ only in what they are allowed to reach.

    QuestionNameOur codeFailure
    “Who are you?” Authentication
    authn    		 requireAuth 401
    “Are you allowed to do this?” Authorization
    authz    		 requireRole 403

    So /admin/ping answers 403 to a provider but 401 to a garbage token. Answering 401 to a wrong-role user would imply “your login is broken” when it is working perfectly — keep the split when you write the US6 access-denial tests. One case looks like 403 and is not: a correctly signed token whose role we never issue. verifyAccessToken throws before requireRole ever runs.

    Layer 01 · src/auth/password.ts

    Passwords are never stored

    Databases leak, and people reuse passwords — so a leak of stored passwords hands over your users' email and bank logins too. We store a hash instead: a one-way function, easy forward and impossible backward. 

    "hunter2"  --hash-->  "$2b$12$XqR7f...(60 chars)"
"hunter2"  <--????--  "$2b$12$XqR7f...(60 chars)"   ← no way back

    This is not encryption — encryption is built to be reversed with a key; hashing has no key and no reverse. Login works without the server ever knowing the password: hash what the user typed, compare the two hashes.

    Why bcrypt and not SHA-256

    It salts automatically. A salt is random data mixed in before hashing. Without it, identical passwords hash identically — crack one "password123" and you have cracked everyone who chose it.

    It is deliberately slow. SHA-256 is built for speed, which is exactly what a cracker wants. bcrypt is built to waste time.

    $2b algorithm $ 12 cost $ XqR7fK2mN9pQ8rS4tU6vW.eY1zA3bC5dE7fG9hI0jK2lM4nO6pQ8 salt + hash, packed together

    The cost is a power of two: SALT_ROUNDS = 12 means 212 = 4,096 iterations, roughly 250 ms per hash. Each +1 doubles the work — unnoticeable once, catastrophic for ten billion guesses. Salt and cost live inside the output, so verifyPassword needs nothing but the stored hash.

    The smoke test proved it — the same password hashed twice gives two different results, and both still verify:

    verify correct  : true
verify wrong    : false
verify empty    : false
salted h1!=h2   : true   ← same password, different hash

    One asymmetry is deliberate: on empty input verifyPassword returns false, but hashPassword throws. An empty password reaching the hasher is a programming error, not a user typo, and should crash loudly.

    Layer 02 · src/auth/jwt.ts

    Tokens carry identity between requests

    Password checking happens once, at login. But HTTP is stateless — the server forgets you the instant it responds, so every later request arrives as a stranger. Instead of resending the password, login issues a token: a signed pass the client attaches to future requests.

    eyJhbGciOiJIUzI1NiJ9 header — algorithm . eyJzdWIiOiJ1LTEiLCJyb2xlIjoiYWRtaW4ifQ payload — the claims . xyQL8SgH_ebyFP6i0rC9RB signature — proof it is genuine

    Three base64 chunks joined by dots. Ours decodes to { "sub": "u-1", "role": "admin", "iat": …, "exp": …, "jti": … } — subject (user id), issued-at, expiry, and a unique token id added in Chapter 02 so logout has something to point at.

    The thing beginners get wrong

    The payload is not encrypted. Base64 is encoding, not secrecy — anyone can paste a token into jwt.io and read it. Never put anything secret in one. Ours holds only a user id and a role, which the user already knows about themselves.

    Then what stops someone editing “provider” into “admin”?

    The signature. When the server signs a token it computes:

    signature = HMAC-SHA256(header + "." + payload, JWT_SECRET)

    JWT_SECRET never leaves the server. On every request jwt.verify recomputes that signature from the token's actual contents and compares, so changing one character breaks the match. The forged-token test proved it: a well-formed role: admin token signed with a guessed secret was rejected at both endpoints.

    Operational consequence

    The secret is the security of the whole system — leak it and anyone can mint admin tokens. Hence .env, gitignored, one secret per environment. Generate your own with the command in .env.example; never share one.

    Expiry, and why revocation is hard

    Tokens are self-contained, which is both strength and weakness: the server keeps no list of issued tokens, so it cannot revoke one individually, and a stolen token works until it expires. Short lifetimes limit the damage — ours default to 1h. Chapter 02 buys revocation back for logout, and accounts for what that cost.

    One real bug worth knowing about

    JavaScript runs all import statements before any other line, so dotenv.config() runs after the import chain. Reading process.env.JWT_SECRET at the top of jwt.ts would get undefined; getSecret() defers the read to the first signature and throws if it is still missing. Signing with undefined would accept everyone's forgeries.

    Layer 03 · src/middleware/auth.ts

    Middleware is the gate in front of the handler

    Express middleware sits before your route handler and decides whether the request continues. Every one has the shape (req, res, next), and exactly one thing must happen — carry on, or answer and stop, never both. They chain left to right, and any link can end the request early. (Chapter 03 changes how a link answers; the gates themselves are unchanged.)

    requireAuth

    The client sends Authorization: Bearer eyJhbGci… — “Bearer” meaning “whoever bears this token gets the access”. No header or the wrong scheme, and we stop. Otherwise we verify and attach the claims to req, the handoff that lets every downstream handler read req.auth without re-parsing anything.

    jwt.verify signals every failure by throwing — bad signature, malformed, expired — so it sits in a try/catch. We answer with one deliberately vague message: telling an attacker which part failed helps them.

    requireRole — a function that returns a function

    Express needs a (req, res, next) function, but we want to configure it per route. So an outer function takes the config and returns the real middleware, which “remembers” allowed — a closure. Hence one call site has parentheses and the other does not: 

    requireAuth,            ← the function itself, Express calls it later
requireRole('admin'),   ← called NOW; its return value is the middleware

    Dropping those parentheses is a classic bug: Express receives the factory instead of the middleware and silently enforces nothing. ...allowed takes any number of roles.

    Why src/types/express.d.ts exists

    req.auth is not a real Express property — we invented it, and TypeScript would reject it. That file performs declaration merging: it reaches into Express's own types and adds our field, so the codebase gets type-checking on req.auth.role.

    Gotcha that will bite you

    tsc reads every file under include, but a runner only compiles what it imports — so npm run dev never saw that augmentation and crashed while npm run typecheck passed. The "ts-node": { "files": true } block in apps/api/tsconfig.json fixed it; dev now runs on tsx, which needs no such flag, so that block is vestigial.

    Where the database actually gets touched

    Put the three pieces together and one property stands out — the one that makes this design scale, and the one that makes revocation hard.

    File map

    packages/shared/index.ts          UserRole + AuthTokenPayload + AuthTokenClaims

apps/api/src/
├── auth/
│   ├── password.ts               hashPassword / verifyPassword
│   ├── jwt.ts                    signAccessToken / verifyAccessToken
│   └── tokenDenylist.ts          revoked sessions — see chapter 02
├── middleware/
│   └── auth.ts                   requireAuth / requireRole
├── types/express.d.ts            teaches TypeScript about req.auth
└── index.ts                      wires middleware onto routes

    The split is worth copying as a habit. auth/ holds pure functions that know nothing about HTTP — callable from a test with no server running. middleware/ is the HTTP adapter. And packages/shared exists so the two apps cannot disagree: backend 'admin' vs frontend 'administrator' is a bug no compiler catches unless UserRole is defined once and imported by both. Chapter 03 adds routes/ and controllers/ above this layer and empties index.ts.

    What does not exist yet

    • No /auth/register and no /auth/login. The ingredients are ready; nothing calls them yet. Both need the Company table first.
    • No database connection. Since resolved — Prisma 7 now talks to Supabase Postgres.
    • No user lookup. /me echoes the token's own claims back; it does not read a real profile. That is US1-4.
    • No refresh tokens. When the 1-hour token expires, the user logs in again. Fine for this sprint.
    • /me and /admin/ping are demonstration routes, proving the middleware works until real endpoints replace them.
    • No test runner anywhere. Root npm test is still an exit 1 stub.

    Try it yourself

    Copy apps/api/.env.example to apps/api/.env, generate a secret with the command inside it, then cd apps/api && npm run dev. In another terminal: 

    curl -i localhost:4000/me                              # 401, no token

TOKEN=$(node -e "require('dotenv').config({quiet:true});
  console.log(require('jsonwebtoken').sign(
    {sub:'u-1',role:'provider'}, process.env.JWT_SECRET,
    {expiresIn:'1h', jwtid:require('crypto').randomUUID()}))")   # jti required since ch. 02

curl -i -H "Authorization: Bearer $TOKEN" localhost:4000/me          # 200
curl -i -H "Authorization: Bearer $TOKEN" localhost:4000/admin/ping  # 403, wrong role

    Paste $TOKEN into jwt.io — you will read the payload instantly, which drives home why nothing secret goes in there. Now change one character in the middle and re-run: 401. That is the signature doing its job.

    Chapter 02

    Ending a session

    Chapter 01 ended on a limitation: a stateless token cannot be taken back. Logout refuses to accept that. This is what it costs to buy revocation back.

    US1-3 b33405e node:crypto randomUUID 8/8 cases verified

    Deleting the token is not logging out

    The obvious implementation is for the frontend to drop the token from localStorage and show the login page again. Nothing was revoked. That token is still signed and unexpired, and requireAuth accepts it, because verification is pure mathematics over the token's own contents. Anyone holding a copy keeps full access for the rest of the hour.

    The thing beginners get wrong

    Client-side cleanup is a UI convenience, not a security boundary. Any logout you can defeat by pressing Back, or by replaying a saved request, was never a logout. The test task “user cannot access protected routes after logout” checks exactly this, and a frontend-only implementation fails it.

    In a classic server-session design this is trivial: the session is a database row, and logout deletes it. We gave that up for speed, so the job is to win back one property — this token stops working now — without giving back the rest.

    Layer 01 · src/auth/jwt.ts

    You cannot revoke what you cannot name

    Two tokens issued to the same user in the same second used to be byte-identical — no way to point at one and say that one is dead. So every token now gets a name: jti, the standard “JWT ID” claim. 

    return jwt.sign(payload, getSecret(), {
    expiresIn: getExpiresIn(),
    jwtid: randomUUID(),          ← new: a unique id per token
});

    Like everything else in the payload it is public, which is fine — a UUID reveals nothing. verifyAccessToken now demands it and returns exp alongside: the next layer needs to know when the token dies to know when it may stop remembering it.

    Why per token and not per user

    We could revoke by user id instead — “everything for u-1 issued before now is dead”. That is what a log out everywhere button wants, but as a default it is wrong: logging out on a library computer would also kick you out on your phone. Naming individual tokens keeps logout scoped to the session in front of you.

    One consequence: tokens minted before this change no longer verify, having no jti. On a live system that is a forced logout for everyone at deploy time. We have no live system yet — this is the kind of change that is free now and expensive in October.

    Layer 02 · src/auth/tokenDenylist.ts

    Remembering the smallest possible thing

    With tokens named, revocation is just a list of the ids that have been logged out — one map, wrapped in two functions, revokeToken(jti, exp) and isTokenRevoked(jti). Nothing outside the file touches it directly. 

    // jti -> token exp, as a UNIX timestamp in seconds.
const revoked = new Map<string, number>();

    Why store the expiry, not just the id

    An entry is only useful while the token it names would otherwise still work: one second after exp, jwt.verify rejects that token anyway. So every write sweeps the map and drops anything past its expiry, bounding the store by how many people logged out in the last hour. Pruning on write rather than on a timer also avoids an interval keeping the Node process alive.

    The trade you just made

    We reintroduced state — the thing Chapter 01 was proud of not having. More precisely, we reintroduced bounded state: a session table holds a row for every active session, while this holds one only for sessions that ended early, and only until they would have ended anyway. Reads stay in memory, so the “never queries the database” property survives.

    Layer 03 · src/middleware/auth.ts

    A third gate in requireAuth

    GateQuestionFailure
    1 Is there a Bearer header at all? 401 malformed header
    2 Is the signature genuine and the token unexpired? 401 invalid or expired
    3 Has this jti been logged out? 401 session has ended

    Gate 3 runs last because it is the only one that costs anything — no reason to check a map for a forged token. All three answer 401: a revoked token establishes no identity, and 403 would imply one. Only the message differs, so a frontend can tell “log in again” from “this request is broken”.

    Gotcha that will bite you

    While adding the gate, one line moved. next() used to sit inside the try that wraps verifyAccessToken: 

    try {
    req.auth = verifyAccessToken(token);
    next();                     ← every downstream error lands in the catch
} catch {
    res.status(401).json({ error: 'Invalid or expired token' });
}

    Express runs the rest of the chain synchronously inside that next(), so a crash in any later handler was caught here and reported as 401 Invalid or expired token — the real error vanished. Verification now sits alone in the try. Watch for this shape wherever you wrap middleware in try/catch.

    Layer 04 · src/index.ts

    The endpoint itself is four lines

    app.post('/auth/logout', requireAuth, (req: Request, res: Response) => {
    revokeToken(req.auth!.jti, req.auth!.exp);
    res.status(204).end();
});

    Every decision in it is about the two words in front of the handler.

    ChoiceWhy
    requireAuth You must prove the session is yours before ending it. Taking a jti from the request body instead would let anyone end anyone's session; reading it off the verified token leaves no parameter to tamper with.
    POST GET is defined to be safe, and the world takes that seriously — browsers prefetch, crawlers follow, and an <img src="/auth/logout"> would silently log your users out.
    204 There is nothing to say. Returning { "ok": true } invents a payload for a client to ignore.
    Second call Answers 401, not 204 — gate 3 stops it before the handler. Non-idempotent in status, but the caller wanted the session gone and it is gone. Assert 401 on the repeat.

    One token, two clocks

    Two lifetimes run at once: the token's, fixed the moment it was signed, and the denylist entry's, which starts at logout and is deliberately cut short to match.

    Where this implementation breaks

    The denylist lives in a JavaScript Map, inside one Node process. Two consequences:

    • It is lost on restart. Every deploy or crash empties it, and a token logged out five minutes ago starts working again for whatever remains of its hour.
    • It is not shared. Run two API instances behind a load balancer and a logout recorded on one is invisible to the other.

    Both are acceptable right now and only right now: one dev process, one machine, no deployment. Shipping this to real users without fixing it would be a bug, so it is written at the top of the file rather than left to be discovered.

    The fix is already shaped: nothing outside tokenDenylist.ts knows the map exists, so swapping it for a Postgres table — (jti primary key, expires_at timestamptz) plus a periodic DELETE WHERE expires_at <= now() — is a change to one file behind the same two functions. Keep the expiry column: it is what stops the table growing forever.

    What changed

    packages/shared/index.ts          + AuthTokenClaims (payload + jti + exp)

apps/api/src/
├── auth/
│   ├── jwt.ts                    mints a jti; verify returns jti + exp
│   └── tokenDenylist.ts          NEW — revokeToken / isTokenRevoked
├── middleware/
│   └── auth.ts                   gate 3; next() moved out of the try
├── types/express.d.ts            req.auth is now AuthTokenClaims
└── index.ts                      POST /auth/logout

    The layering from Chapter 01 held up, which is the useful signal. tokenDenylist.ts went into auth/ because it is a pure function over ids and timestamps — no Request, no Response. Adding a feature meant adding one file in the layer it belonged to.

    Verified behavior

    Run against a live server: two tokens minted, a provider and an admin, and the provider's logged out. These are the shapes the four US1-3 test tasks should assert.

    RouteRequestResult
    /mevalid provider — before logout200
    /admin/pingvalid admin — before logout200
    /auth/logoutvalid provider204

    The sixth row is the one worth staring at: the admin session was never touched by the provider's logout. That is per-token revocation doing its job.

    What does not exist yet

    • Nothing issues the tokens this revokes. There is still no /auth/login, so every token above was minted by hand in a script.
    • The denylist does not survive a restart, and is not shared between instances — the one item here that is a defect rather than unbuilt scope.
    • No “log out everywhere”. Revocation is per token by design; ending every session for an account needs a per-user index or a “tokens issued before t are void” marker.
    • No client-side session cleanup and no redirect. That is the frontend half of US1-3 — the server ends the session, but nothing clears the browser or sends the user to the login page.
    • Still no test runner, so the four US1-3 test tasks have nowhere to live. The table above came from a shell script: evidence, not a regression suite. Chapter 03 splits app.ts out so one can be added.

    Try it yourself

    Start the API as in Chapter 01, mint a token the same way, then:

    curl -i -H "Authorization: Bearer $TOKEN" localhost:4000/me   # 200

curl -i -X POST -H "Authorization: Bearer $TOKEN" \
  localhost:4000/auth/logout                                  # 204, no body

curl -i -H "Authorization: Bearer $TOKEN" localhost:4000/me   # 401 Session has ended

    Paste the token into jwt.io again: the signature still verifies and exp is still in the future, so by every rule in Chapter 01 it is valid. It is refused anyway, and the only reason is a UUID in a map on the server. That gap between “cryptographically valid” and “accepted” is the whole chapter. Then restart the server and replay the last curl: it answers 200, because the denylist went with the process.

    Chapter 03

    One shape for every endpoint

    Nine people are about to write endpoints into this API at the same time. This is the agreement they write them against: where the code goes, how a failure comes back, how input is checked.

    every story from here on 64d67e8 zod 4 9/9 cases verified

    The same failure, described three ways

    Chapters 01 and 02 put four routes straight into src/index.ts. Fine for four. But registration, login and the profile endpoints are being written right now, by different people, and nothing said what a failure should look like — so each would have invented one: 

    { "error": "Username already taken" }
{ "message": "username taken", "ok": false }
{ "errors": [ { "username": "taken" } ] }

    All three are reasonable. Together they cost the frontend three code paths for one event, and the third arrives as a form that silently fails to show its error. The fix is boring, and it only works if it lands before the endpoints do.

    Layer 01 · packages/shared/index.ts

    Every failure returns the same body

    {
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Request body is invalid",
    "details": [ { "field": "email", "message": "Invalid email address" } ]
  }
}

    Three fields, and the split between them is the point. code is for the program — a fixed string the frontend switches on. message is for a human reading a log. details appears only when individual fields were rejected, so a form can put each message beside the input it belongs to instead of dumping them all in one banner.

    CodeStatusUse for
    BAD_REQUEST400Malformed request that is not about one field
    VALIDATION_FAILED400Field-level rejection — carries details
    UNAUTHORIZED401No token, bad token, ended session
    FORBIDDEN403Authenticated, but this role may not
    NOT_FOUND404Unknown route, or a missing resource
    CONFLICT409Existing data blocks the write — a taken username
    INTERNAL500A bug. Never thrown deliberately

    The 401/403 split from Chapter 01 survives intact — UNAUTHORIZED means “we do not know who you are”, FORBIDDEN means “we know, and no”.

    A frontend that switches on code breaks silently when a code is renamed, so the list lives in @mangodb/shared and both apps import it — the same move UserRole made in Chapter 01. Rename one now and TypeScript fails the build on both sides, instead of the bug reaching a user.

    Layer 02 · src/lib/ApiError.ts · src/middleware/errorHandler.ts

    Handlers stopped answering failures

    An agreed shape that every handler formats by hand holds until the first person forgets. So handlers no longer format failures at all. They throw one: 

    throw ApiError.conflict('Username already taken');

    A single terminal middleware, mounted after every route, catches those and writes the envelope. It is the only place in the API allowed to set a 4xx or 5xx status — which turns “did they use the right shape?” from a review question into something that cannot go wrong.

    Express 5 is what makes this cheap: it forwards a rejected promise from an async handler to the error middleware by itself. In Express 4 every async route needed its own try/catch or a wrapper, and a forgotten one left the request hanging until it timed out. Ours need neither — throw is the whole API.

    The half you get for free

    Anything that is not an ApiError is a bug nobody planned for — a Prisma failure, a null dereference. Those are logged on the server and answered with a bare INTERNAL. Stack traces, SQL and table names stop at the boundary, and no handler has to remember to make that happen.

    Layer 03 · src/middleware/validate.ts

    Input is described, not inspected

    Hand-written checks — if (!body.email) … — drift between endpoints, miss cases, and tell TypeScript nothing, so the code below them still treats the body as any. A schema replaces all three problems at once: 

    const registerSchema = z.object({
    username: z.string().min(3).max(50),
    email: z.email().max(100),
    password: z.string().min(8),
});

const body = parseBody(registerSchema, req.body);   ← typed, or it throws

    body.email is a string as far as the compiler is concerned, and bad input never reaches the next line: parseBody throws VALIDATION_FAILED with one details entry per bad field, which is already the shape the registration form needs.

    Why this is a function and not middleware

    The conventional Express answer is middleware — router.post('/register', validate(schema), register) — and it reads better in the route file. But middleware has nowhere to put the parsed value except back on req.body, which Express types as any. The handler then needs a cast, and a cast is a promise the compiler cannot check. Calling the parser inside the handler keeps the schema's type all the way down. We traded a visible route contract for a type the compiler enforces.

    Where code goes now

    apps/api/src/
├── index.ts              6 lines — listens, nothing else
├── app.ts                builds the app; does not listen
├── env.ts                loads .env — first import, always
├── routes/               paths + middleware, no logic
├── controllers/          the work
├── middleware/           auth · errorHandler · validate
├── lib/                  ApiError · prisma
└── auth/                 unchanged since chapter 02

    Adding an endpoint is three steps: write the handler in controllers/, wire the path in routes/, and mount the router once in routes/index.ts if the area is new. Two files above are less obvious.

    app.ts builds the app but never calls listen. A test can import it and drive it in-process — no port, no running server, no cleanup. Chapters 01 and 02 both ended on “still no test runner”; this is the shape that lets one be added without touching any route.

    env.ts must be the first import in an entry point. Chapter 01 hit this with JWT_SECRET and solved it by deferring the read until first use. lib/prisma.ts cannot defer — it opens the connection while it is being imported — so load order is the fix here, which is fragile enough to be worth the comment sitting on it.

    apps/api/README.md carries the same rules as a checklist with a copyable endpoint. Read that before adding a route; read this chapter to know why it says what it says.

    Run against a live server after the refactor. Every path and status code is unchanged from Chapters 01 and 02 — only the body of a failure is different, which is the result worth checking.

    RouteRequestResult
    /healthnone needed200
    /nopepath does not exist404 NOT_FOUND
    /meno header401 UNAUTHORIZED
    /meBearer garbage401 UNAUTHORIZED

    What does not exist yet

    • Nothing uses the convention yet. Registration, login and the profile endpoints are still being written. The only routes in the tree are the demonstration ones from Chapters 01 and 02.
    • Still no test runner. npm test is an exit 1 stub in the root and in apps/api. app.ts is now shaped for supertest; nobody has added it.
    • No table an administrator could live in. UserRole has included 'admin' since Chapter 01, but the Prisma schema has no admin — so US6-1 has an endpoint to write and nothing to authenticate against.
    • No success envelope, deliberately. A successful response returns the resource itself. Wrapping it in { "data": … } buys nothing and costs every caller a hop.
    • No rate limiting and no request logging. Both belong at this layer; neither is written.

    Try it yourself

    Start the API as in Chapter 01, then ask it for two unrelated failures:

    curl -s localhost:4000/nope
{"error":{"code":"NOT_FOUND","message":"Cannot GET /nope"}}

curl -s localhost:4000/me
{"error":{"code":"UNAUTHORIZED","message":"Missing or malformed Authorization header"}}

    A typo'd URL and a missing token, raised by two different files, arriving in one shape — and neither handler formatted a thing. Worth seeing once before you write an endpoint that depends on it.
