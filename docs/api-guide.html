Start

How do I run the API?

Copy .env.example, fill three values, npm run dev.

cd apps/api
cp .env.example .env      # then set JWT_SECRET, DATABASE_URL, DIRECT_URL
npm run db:generate       # regenerate Prisma Client after any schema change
npm run dev               # http://localhost:4000
npm run typecheck         # must pass before you open a PR

Generate your own JWT_SECRET with the command inside .env.example. Never share one between people or environments.

How do I add an endpoint?

Schema in schemas/, handler in controllers/, path in routes/, mount once in routes/index.ts.

// schemas/company.schema.ts
export const updateSchema = z.object({
    company_name: z.string().min(1).max(255),
    email: z.email().max(100),
});

// controllers/company.controller.ts
export async function updateProfile(req: Request, res: Response) {
    const body = parseBody(updateSchema, req.body);   // typed, or throws

    const company = await prisma.company.findUnique({
        where: { company_id: Number(req.auth!.sub) },
    });
    if (!company) throw ApiError.notFound('Company not found');

    res.json(await prisma.company.update({
        where: { company_id: company.company_id }, data: body,
    }));
}

// routes/company.routes.ts
companyRoutes.patch('/me', requireAuth, updateProfile);

No try/catch and no async wrapper — Express 5 forwards a rejected promise to the error handler by itself. Keep the controller to handlers: a response shape or an error translation that a second endpoint would want belongs in lib/.

What happens to a request?

Two gates, then your handler. Every failure exits through one place.

Errors

How do I return an error?

Throw an ApiError. Never call res.status(4xx) yourself.

throw ApiError.conflict('Username already taken');
throw ApiError.notFound('Company not found');
throw ApiError.forbidden();

errorHandler is the only place in the API that sets a 4xx or 5xx status. That is what makes “did they use the right shape?” impossible to get wrong instead of a review question.

What does an error look like?

Always this, for every non-2xx response.

{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Request body is invalid",
    "details": [ { "field": "email", "message": "Invalid email address" } ]
  }
}
  • code — for the program. The frontend switches on it.
  • message — for a human reading a log. Reword it freely.
  • details — only when individual fields failed, so a form can put each message beside its own input.

Success responses return the resource itself, unwrapped — res.json(company), never { data: company }. 204 with no body for a delete or a logout.

Which code do I use?

Seven, and they are the whole vocabulary.

CodeStatusUse for
BAD_REQUEST400Malformed, but not about one field
VALIDATION_FAILED400Field-level rejection — carries details
UNAUTHORIZED401No token, bad token, ended session
FORBIDDEN403Authenticated, but this role may not
NOT_FOUND404Unknown route, or a missing resource
CONFLICT409Existing data blocks the write — a taken username
INTERNAL500A bug. Never thrown by hand

Codes are a contract with the frontend, so they live in @mangodb/shared and both apps import them. Renaming one fails the build on both sides instead of reaching a user.

401 or 403?

401 = we do not know who you are. 403 = we know, and no.

A missing or broken token is never 403 — that would tell a user their login is broken when it is working perfectly. One case looks like 403 and is not: a correctly signed token carrying a role we never issue is 401, because verifyAccessToken rejects it before requireRole ever runs.

Input

How do I validate a request body?

Write a zod schema, call parseBody. Never hand-write if (!body.x).

// schemas/auth.schema.ts
export const registerSchema = z.object({
    username: z.string().min(3).max(50),
    email: z.email().max(100),
    password: z.string().min(8),
});

// the controller
const body = parseBody(registerSchema, req.body);   // typed, or throws

body.email is now a string to the compiler, and bad input never reaches the next line — parseBody throws VALIDATION_FAILED with one details entry per bad field, which is already the shape a form needs. For query strings use parseQuery, and reach for z.coerce — every query value arrives as a string.

Why isn't validation middleware?

Middleware would have to hand the parsed value back through req.body, which Express types as any.

The handler would then need a cast, and a cast is a promise the compiler cannot check. Calling the parser inside the handler keeps the schema's type all the way down. The cost is that the route file no longer shows the contract — a deliberate trade.

Auth

How do I protect a route?

requireAuth first, then requireRole. Order is not optional.

companyRoutes.get('/me', requireAuth, getMyProfile);

// admin routers guard once, so a new route cannot miss the check
adminRoutes.use(requireAuth, requireRole('admin'));

requireRole is a factory — it takes the roles and returns the middleware, so the parentheses are required. Dropping them hands Express the factory, which silently enforces nothing. It takes any number of roles: requireRole('provider', 'receiver').

How do I know who is calling?

req.auth, set by requireAuth: { sub, role, jti, exp }.

sub is the user id, role is one of provider | receiver | both | admin — see what a role grants. req.auth is not a real Express property — src/types/express.d.ts merges it into Express's own types so TypeScript accepts it.

Why is my token rejected?

Three gates, all answering 401. The message tells you which one.

MessageMeans
Missing or malformed Authorization headerNo header, or not Bearer <token>
Invalid or expired tokenBad signature, malformed, past exp, or a role we never issue
Session has endedSignature is fine — this token was logged out

Tokens minted before jti was added no longer verify at all. If you have a token saved from an old session, mint a new one.

What is in a token, and what protects it?

Public claims, protected by a signature — not by secrecy.

{ "sub": "u-1", "role": "provider", "iat": …, "exp": …, "jti": … }
  • The payload is not encrypted. Base64 is encoding. Anyone can paste a token into jwt.io and read it, so nothing secret goes in one.
  • The signature is what stops edits. HMAC-SHA256(header.payload, JWT_SECRET) is recomputed on every request; change one character and it stops matching.
  • The secret is the security of the whole system. Leak it and anyone can mint admin tokens. One per environment, in .env, gitignored.
  • They expire in 1h and there are no refresh tokens — the user logs in again.

How are passwords stored?

bcrypt hashes at cost 12. The plaintext is never stored and never recoverable.

$2b$12$XqR7fK2mN9pQ8rS4tU6vW.eY1zA3bC5dE7fG9hI0jK2lM4nO6pQ8
 ↑    ↑  ↑
 alg  cost salt + hash, packed together

bcrypt salts automatically, so two identical passwords produce different hashes and one cracked "password123" does not crack everyone. It is also deliberately slow — cost 12 means 212 iterations, ~250 ms per hash. The salt and cost live inside the output, so verifyPassword needs nothing but the stored hash. One asymmetry on empty input: verifyPassword returns false, but hashPassword throws — an empty password reaching the hasher is a bug, not a typo.

How does logout actually end a session?

POST /auth/logout puts the token's jti on a denylist. requireAuth then rejects it.

Clearing localStorage on the frontend revokes nothing — that token stays signed and unexpired, and anyone holding a copy keeps access for the rest of the hour. The endpoint takes the jti off the verified token, not the body, so nobody can end someone else's session. It answers 204; a second call with the same token answers 401, because gate 3 stops it before the handler. Revocation is per token, so logging out on one device leaves your other sessions alone.

Where does the denylist break?

It is a Map in one Node process: lost on restart, not shared between instances.

A token logged out five minutes ago starts working again after a deploy, and a logout recorded on one instance is invisible to another. Acceptable for one dev process and nothing else. The fix is contained — nothing outside tokenDenylist.ts knows the map exists, so a Postgres table (jti primary key, expires_at timestamptz) behind the same two functions is a one-file change. Keep the expiry column; it is what stops the table growing forever.

Accounts

How does a company register?

POST /auth/register, public, returns 201 with the company and a token.

curl -s -X POST localhost:4000/auth/register -H 'content-type: application/json' -d '{
  "company_name": "CodeCrafters", "username": "codecrafters",
  "email": "contact@codecrafters.com", "password": "correct horse battery",
  "phone": "021111111", "account_type": "PROVIDER",
  "company_type": ["SME", "Software House"]
}'

{"company":{"company_id":33,"company_name":"CodeCrafters","username":"codecrafters",
 "email":"contact@codecrafters.com","account_type":"PROVIDER",
 "company_type":["SME","Software House"], ...},
 "accessToken":"eyJhbGciOiJIUzI1NiIs..."}

This is the one response in the API that wraps its resource. Everything else returns the object itself; register returns two things, because it also logs you in — the token it returns is the same one /companies/me accepts, so the frontend does not have to call login straight after signup. company_description, address, and website are the only optional fields. The password hash is never in the response: the handler names the columns it returns with an explicit select rather than deleting the field afterwards.

What is account_type, and how is it different from company_type?

account_type is one of PROVIDER, RECEIVER, BOTH. company_type is repeatable industry tags.

They read alike and are not alike. account_type is a single uppercase discriminator on company, and it decides which subtype row the company gets: PROVIDER gets a row in provider, RECEIVER one in receiver, and BOTH gets both. The seeded database follows that without exception — 9 providers, 9 receivers, 2 BOTH companies carrying both rows — and register keeps it, creating the company, its tags, and its subtype rows in one nested create, which is one transaction.

company_type lives in its own table, many rows per company: SME, Software House, FinTech, AI Lab, 16 distinct values in the seed data. Registration requires at least one. There is no ADMIN account type — the enum rejects it, so nobody can register themselves an admin.

How does a BOTH company pass a provider-only route?

requireRole compares what the role grants, not the role itself.

// src/auth/roles.ts
both: ['provider', 'receiver', 'both'],
admin: ['admin'],

The token role comes from account_type — BOTH becomes 'both' — and asking what a role may act as is a separate question from what it is. Without this a BOTH company would get 403 on both kinds of route, which is the opposite of what it signed up for. Note that admin grants only admin: it is not a superset, and a BOTH token still gets 403 from /admin/ping.

What happens when the username is already taken?

409 CONFLICT, with the offending field in details.

{"error":{"code":"CONFLICT","message":"Username or email already registered",
  "details":[{"field":"username","message":"This username is already registered"}]}}

Two things check, and both matter. assertCompanyIdentityAvailable in lib/companyIdentity.ts runs a case-insensitive lookup before the insert — that is the one that can report both username and email in details, since an index only fails on whichever column it reaches first.

The unique indexes are still the enforcement. Two registrations claiming one username can both clear the pre-check; the loser's insert is rejected, Prisma reports P2002, and the handler turns that into the same envelope. Reading the field out takes a little care: through the driver adapter the columns arrive as the index name (company_username_key) rather than in meta.target.

Register lowercases username and email before writing, because the Postgres unique index is case-sensitive — without that, CodeCrafters would register happily alongside codecrafters.

How does a company edit its profile?

PATCH /companies/me. Send only what changed; null clears a nullable column.

curl -s -X PATCH localhost:4000/companies/me -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' -d '{
  "company_name": "CodeCrafters Co., Ltd.",
  "address": null,
  "company_type": ["SME", "AI Lab"]
}'

Three states, not two. A field that is absent leaves its column alone — that is what makes this a PATCH, and it is why the edit form may send one input or all of them. A field carrying a value overwrites. A field set to null clears, and only company_description, address, and website accept it, because they are the only nullable columns; null anywhere else is a 400. An empty body is a 400 too — it is a client bug, not a no-op worth a 200.

company_type is a set, not a list you append to: the request carries the whole set and the tags it replaces are deleted. It is a nested write, so the delete and the create are one transaction and the company is never briefly untagged. Note the schema's .min(1) — there is no way to spend an edit removing every tag.

username and email are editable, and the same 409 and the same details shape as registration apply — see what happens when the username is already taken. The one difference is excludeCompanyId: assertCompanyIdentityAvailable skips the caller's own row, or a form that re-submits every field would collide with itself.

password and account_type are not editable here, and the schema strips them silently rather than rejecting the request. A password change needs the current password, which is a different endpoint. account_type decides which subtype rows a company owns and what its token's role claim says, so changing it means writing provider/receiver rows and issuing a new token — also a different endpoint.

The response is the whole CompanyProfile, the same body GET /companies/me returns, so the form can render the saved state without a second request. Read-only mode is the frontend's job: the API has no draft state, and a profile the user is only looking at is simply one nobody sent a PATCH for.

Layout

Where does code go?

Routes hold paths, controllers hold work, and nothing else holds either.

packages/shared/index.ts   UserRole · AccountType · CompanyProfile · ApiErrorCode · ApiErrorResponse

apps/api/src/
├── index.ts               6 lines — listens, nothing else
├── app.ts                 builds the app; does not listen
├── env.ts                 loads .env — first import, always
├── routes/                paths + middleware, no logic
├── controllers/           handlers, and nothing but handlers
├── schemas/               zod request schemas, one file per area
├── middleware/            auth · errorHandler · validate
├── lib/                   ApiError · prisma · prismaErrors · companyProfile · companyIdentity
├── auth/                  password · jwt · roles · tokenDenylist — pure, no HTTP
└── types/express.d.ts     teaches TypeScript about req.auth

auth/ holds pure functions that know nothing about HTTP, so a test can call them with no server running. middleware/ is the HTTP adapter. A controller that grows past its handlers is a sign something belongs in lib/: the register handler's response shape lives in lib/companyProfile.ts and its error translation in lib/prismaErrors.ts, so US1-4 does not rewrite either. packages/shared exists so the two apps cannot disagree — backend 'admin' vs frontend 'administrator' is a bug no compiler catches unless the type is defined once and imported by both.

Why is app.ts separate from index.ts?

app.ts builds the app but never calls listen, so a test can drive it with no port.

index.ts is the only file that opens a socket. This is the shape supertest needs; it exists so a test runner can be added without touching a single route.

Gotchas

Env vars are undefined

JavaScript runs every import before any other line, so dotenv loads after the import chain.

Two fixes coexist. jwt.ts defers the read: getSecret() reads JWT_SECRET at first use and throws if it is missing — signing with undefined would accept everyone's forgeries. lib/prisma.ts cannot defer, because it opens the connection while being imported, so load order is the fix: import './env' must be the first line of any entry point.

next() inside a try swallows every later error

Express runs the rest of the chain synchronously inside next(), so your catch catches their bugs.

try {
    req.auth = verifyAccessToken(token);
    next();                  // ← every downstream crash lands in the catch below
} catch {
    // a valid login gets told its token is bad; the real error vanishes
}

Keep only the throwing call inside the try and call next() after it. Watch for this shape wherever middleware wraps anything in try/catch.

Cannot find module '../generated/prisma/client'

Prettier formatted the generated client, then lint-staged's stash cleanup deleted it on commit.

npm run db:generate --workspace apps/api

The root .prettierignore now excludes apps/api/src/generated, so it should not recur. The directory is gitignored, so CI regenerates it before typecheck.

typecheck passes but dev crashes

tsc reads every file under include; a runner only compiles what it imports.

So src/types/express.d.ts was invisible to npm run dev. The "ts-node": { "files": true } block in tsconfig.json fixed it; dev now runs on tsx, which needs no such flag, so that block is vestigial.

Try it yourself

Two unrelated failures, one shape, and no handler formatted either.

curl -s localhost:4000/nope
{"error":{"code":"NOT_FOUND","message":"Cannot GET /nope"}}

curl -s localhost:4000/companies/me
{"error":{"code":"UNAUTHORIZED","message":"Missing or malformed Authorization header"}}

The quickest real token is now a registration — accessToken comes back in the response. To mint one by hand instead, while there is still no login endpoint:

cd apps/api
TOKEN=$(npx tsx -e "import './src/env';
  import {signAccessToken} from './src/auth/jwt';
  console.log(signAccessToken({sub:'1',role:'provider'}))")

curl -s -H "Authorization: Bearer $TOKEN" localhost:4000/companies/me   # 200
curl -s -H "Authorization: Bearer $TOKEN" localhost:4000/admin/ping  # 403

Missing

What does not exist yet?

Read this before assuming something works.

  • No /auth/login. /auth/register exists and returns a token, so a brand-new company can call the API — but an existing one has no way back in. That is US1-2.
  • The seeded companies cannot log in even once login lands. All 20 carry the literal string hash123 in password, not a bcrypt hash, so verifyPassword rejects every one of them. The seed has to be rewritten.
  • No test runner. npm test is an exit 1 stub in the root and in apps/api. The table above came from a shell script — evidence, not a regression suite.
  • No table an administrator could live in. UserRole includes 'admin', but the Prisma schema has no admin and account_type has no ADMIN value, so US6-1 has nothing to authenticate against.
  • The denylist does not survive a restart and is not shared between instances — the one item here that is a defect rather than unbuilt scope.
  • No “log out everywhere”, no refresh tokens, no rate limiting, no request logging.
  • No client-side session cleanup or redirect. The server ends the session; nothing clears the browser.
  • /admin/ping is a demonstration route, alive only until real endpoints replace it. /me is gone — US1-4 replaced it with GET /companies/me, and US1-5 added PATCH beside it.
  • No way to change a password or an account_type. PATCH /companies/me edits everything else; both of those need an endpoint of their own.

No entry matches that. Try a status code, a file name, or a word from an error message.
