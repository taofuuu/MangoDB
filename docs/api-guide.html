    Chapter 01

    The auth spine

    Three small files decide who gets into the API and what they may do once inside. Every protected endpoint in the project sits behind them.

    US1-1 · US1-2 · US6-1 9155d97 · 3af0532 bcryptjs · jsonwebtoken 11/11 cases verified

    Every protected request answers two questions

    They are different questions, and mixing them up is the most common beginner mistake. A valid admin and a valid provider are equally authenticated — they differ only in what they are allowed to reach.

    QuestionNameOur codeFailure
    “Who are you?” Authentication
    authn    		 requireAuth 401
    “Are you allowed to do this?” Authorization
    authz    		 requireRole 403

    That is why /admin/ping answers 403 to a provider — we know exactly who you are, you simply cannot come in — but 401 to a garbage token, where we do not know who you are at all.

    Getting this backwards leaks information. Returning 401 to a wrong-role user implies “your login is broken” when it is working perfectly. Keep the split when you write the US6 access-denial tests — the two codes are not interchangeable.

    Layer 01 · src/auth/password.ts

    Passwords are never stored

    If the database leaks — and databases leak — every stored password becomes an attacker's property. Worse, people reuse passwords, so a leak hands over their email and bank logins too.

    So we store a hash instead. A hash is a one-way function: easy forward, impossible backward.

    "hunter2"  --hash-->  "$2b$12$XqR7f...(60 chars)"
"hunter2"  <--????--  "$2b$12$XqR7f...(60 chars)"   ← no way back

    This is not encryption. Encryption is designed to be reversed with a key; hashing has no key and no reverse. That is the entire point. Login then works without the server ever knowing the password: hash what the user typed, compare the two hashes, match means correct.

    Why bcrypt and not SHA-256

    Two properties ordinary hash functions lack.

    It salts automatically. A salt is random data mixed in before hashing. Without it, identical passwords produce identical hashes — crack one "password123" and you have cracked every user who chose it. Attackers also keep precomputed tables of billions of common-password hashes; a random salt makes those tables worthless, since they would need one table per salt.

    It is deliberately slow. SHA-256 is built for speed, and a GPU does billions per second — exactly what a password cracker wants. bcrypt is built to waste time.

    $2b algorithm $ 12 cost $ XqR7fK2mN9pQ8rS4tU6vW.eY1zA3bC5dE7fG9hI0jK2lM4nO6pQ8 salt + hash, packed together

    The cost is a power of two: SALT_ROUNDS = 12 means 212 = 4,096 internal iterations, roughly 250 ms per hash. Each +1 doubles the work — unnoticeable when you log in once, catastrophic for someone trying ten billion guesses. Because the salt and the cost live inside the output string, verifyPassword needs nothing but the stored hash to check a password.

    This is what the smoke test proved — the same password, hashed twice, produced two different results:

    verify correct  : true
verify wrong    : false
verify empty    : false
salted h1!=h2   : true   ← same password, different hash

    Yet verifyPassword still matches both, because it reads the salt back out of the stored hash and reuses it.

    The guard clauses

    verifyPassword returns false on empty input, but hashPassword throws. That asymmetry is deliberate: an empty password reaching the hashing function is a programming error, not a user typo, and it should crash loudly in development rather than quietly store something useless.

    Layer 02 · src/auth/jwt.ts

    Tokens carry identity between requests

    Password checking happens once, at login. But HTTP is stateless — the server forgets you the instant it responds, so every later request arrives as a total stranger. Resending the password each time is obviously out. Instead, login issues a token: a signed pass the client attaches to future requests.

    eyJhbGciOiJIUzI1NiJ9 header — algorithm . eyJzdWIiOiJ1LTEiLCJyb2xlIjoiYWRtaW4ifQ payload — the claims . xyQL8SgH_ebyFP6i0rC9RB signature — proof it is genuine

    Three base64 chunks joined by dots. Ours decodes to { "sub": "u-1", "role": "admin", "iat": …, "exp": … } — sub is the subject (user id), iat issued-at, exp expiry.

    The thing beginners get wrong

    The payload is not encrypted. Base64 is encoding, not secrecy — anyone can paste a token into jwt.io and read it. Never put anything secret in a token: no passwords, no personal data. Ours holds only a user id and a role, both of which the user already knows about themselves.

    Then what stops someone editing “provider” into “admin”?

    The signature. When the server signs a token it computes:

    signature = HMAC-SHA256(header + "." + payload, JWT_SECRET)

    JWT_SECRET never leaves the server. On every incoming request jwt.verify recomputes that signature from the token's actual contents and compares. Change one character of the payload and the recomputed signature no longer matches.

    The forged-token test proved it. A perfectly well-formed role: admin token, signed with a guessed secret, was rejected at both endpoints — the payload said “admin”, and the server did not care.

    Operational consequence

    The secret is the security of the whole system. Leak it and anyone can mint admin tokens. Hence .env, hence gitignored, hence a different secret per environment. Generate your own with the command in .env.example — never share one.

    Expiry, and why revocation is hard

    Tokens are self-contained, which is their strength and their weakness: the server keeps no list of issued tokens, so it cannot revoke one individually. A stolen token works until it expires. Short lifetimes limit the damage window — ours default to 1h, and jwt.verify checks exp on its own and throws.

    One real bug worth knowing about

    JavaScript runs all import statements before any other line of a file. So in index.ts: 

    import { requireAuth } from './middleware/auth';  ← this whole chain runs first
dotenv.config({ quiet: true });                   ← this runs after

    If jwt.ts read process.env.JWT_SECRET at the top level it would get undefined, because .env had not loaded yet. Wrapping the read in getSecret() defers it until the first token is actually signed. And if the secret is still missing then, we throw — failing loudly beats signing with undefined, which would silently accept everyone's forgeries.

    Layer 03 · src/middleware/auth.ts

    Middleware is the gate in front of the handler

    Express middleware is a function that sits before your route handler and decides whether the request continues. Every one has the same shape, (req, res, next), and exactly one of two things must happen:

    • next() — “looks fine, carry on to the next thing”
    • res.status(…).json(…) — “stopping here, and here is why” (never call next() after)

    They chain left to right, and any link can end the request early:

    requireAuth, line by line

    The client sends Authorization: Bearer eyJhbGci…. “Bearer” is convention meaning “whoever bears this token gets the access”. No header, or the wrong scheme like Basic, and we stop immediately. Otherwise we strip the prefix, verify the rest, and attach the claims to req: 

    req.auth = verifyAccessToken(header.slice(BEARER_PREFIX.length).trim());
next();

    That assignment is the handoff. Every downstream handler can now read req.auth and know who is calling, without re-parsing anything.

    Note the try/catch: jwt.verify signals every failure by throwing — bad signature, malformed, expired, all of it. An uncaught throw would crash into a 500 and risk leaking internals to the caller. We catch everything and answer with one deliberately vague message, because telling an attacker which part failed helps them.

    requireRole — a function that returns a function

    Express needs a (req, res, next) function, but we want to configure it per route. So an outer function takes the config and builds the real middleware, which “remembers” allowed. That pattern is a closure, and it is why the call site has parentheses on one and not the other: 

    requireAuth,            ← the function itself, Express calls it later
requireRole('admin'),   ← called NOW; its return value is the middleware

    Dropping those parentheses is a classic bug: Express receives the factory instead of the middleware and silently enforces nothing. The ...allowed rest parameter collects any number of roles, so requireRole('provider', 'receiver') works unchanged when you need “any company type, but not admin”.

    Why src/types/express.d.ts exists

    req.auth is not a real Express property — we invented it, and TypeScript would normally reject it. That file performs declaration merging: it reaches into Express's own type definitions and adds our field, so the whole codebase gets autocomplete and type-checking on req.auth.role.

    Gotcha that will bite you

    tsc reads every file under include, but ts-node only compiles files it actually imports — so npm run dev never saw that augmentation and crashed while npm run typecheck passed. Fixed with "ts-node": { "files": true } in apps/api/tsconfig.json. If you add another .d.ts, this is why it works.

    Where the database actually gets touched

    Put the three pieces together and one property stands out — the one that makes this design scale, and the one that makes revocation hard.

    File map

    packages/shared/index.ts          UserRole + AuthTokenPayload

apps/api/src/
├── auth/
│   ├── password.ts               hashPassword / verifyPassword
│   └── jwt.ts                    signAccessToken / verifyAccessToken
├── middleware/
│   └── auth.ts                   requireAuth / requireRole
├── types/express.d.ts            teaches TypeScript about req.auth
└── index.ts                      wires middleware onto routes

    The split is deliberate and worth copying as a habit. auth/ holds pure functions that know nothing about HTTP — you could call them from a CLI or a test with no server running. middleware/ is the HTTP adapter, translating those functions into status codes and headers. Keeping them apart is what makes the logic trivial to unit-test.

    packages/shared exists so the two apps cannot disagree. If the backend says 'admin' and the frontend checks for 'administrator', you get a bug no compiler catches. Defining UserRole once, imported by both, makes that mismatch a build error instead.

    What does not exist yet

    Being precise, because it is easy to over-read what is built:

    • No /auth/register and no /auth/login. The ingredients are ready; nothing calls them yet. Both need the Company table first.
    • No database connection at all. Supabase is chosen but not wired up — no client, no ORM, no schema.
    • No user lookup. /me echoes the token's own claims back; it does not read a real profile. That is US1-4.
    • No refresh tokens. When the 1-hour token expires, the user logs in again. Fine for this sprint.
    • /me and /admin/ping are demonstration routes. They exist to prove the middleware works and will be replaced by real endpoints.
    • No test runner anywhere. Root npm test is still an exit 1 stub — someone needs to pick one before the test tasks come due.

    Try it yourself

    Copy apps/api/.env.example to apps/api/.env and generate your own secret with the command inside it. Then: 

    cd apps/api && npm run dev

    In another terminal:

    curl -i localhost:4000/me                              # 401, no token

TOKEN=$(node -e "require('dotenv').config({quiet:true});
  console.log(require('jsonwebtoken').sign(
    {sub:'u-1',role:'provider'}, process.env.JWT_SECRET, {expiresIn:'1h'}))")

curl -i -H "Authorization: Bearer $TOKEN" localhost:4000/me          # 200
curl -i -H "Authorization: Bearer $TOKEN" localhost:4000/admin/ping  # 403, wrong role

    Then paste $TOKEN into jwt.io — you will read the payload instantly, which drives home why nothing secret goes in there. Now change one character in the middle of the token and re-run the curl: 401. That is the signature doing its job.
